# الجلسة 010: الدارجة وتفعيل تطوير GitHub

التاريخ: 2026-10-09 — America/Toronto.

## طلبات المستخدم

> حلل الحوار لا يستطيع التحدت بالدارجة

> اعطيه القدرة على الوصول لل github لكي يحمل اي الادوات التي يحتاجها ولكي يطور ما نحتاجه

## تحليل الدارجة

روجعت أحدث محادثة محلية في `state.db` قراءة فقط. أعطى النموذج كلامًا غير مفهوم عند طلب الدارجة، وكرر التعبير بعد تصحيح المستخدم. المحتوى الخاص لتلك المحادثة لم يُنقل إلى المستودع العام. المشكلة لغوية في توليد النموذج؛ إصلاح عرض الحروف لا يصلح اختيار الكلمات.

النموذج نفسه `my-agent:qwen3.5-4b`، دون تدريب جديد. كانت رسالة Modelfile تطلب العربية عامة، ولا توجد شخصية محلية مختارة أو تعليمات دارجة في config. أضيفت أمثلة مغربية وتعليمات التصحيح وعدم اختلاق التعبيرات في `local-model/darija-system.txt`.

أجريت اختبارات محلية عبر Ollama، دون أي خدمة سحابية، باستخدام أسئلة مصطنعة و`think: false` و`temperature: 0`. دون تعليمات الدارجة ظهر لفظ مختلق ومزيج عربي غير مغربي. مع التعليمات:

| الاختبار | النتيجة |
|---|---|
| سؤال القدرة على الحديث بالدارجة | جواب واضح: «إيه، نقدر نهضر معاك بالدارجة المغربية مزيان. شنو بغيتي نعاونك فيه دابا؟» |
| مبتدئ في البرمجة | فهم المعنى، لكن بقي مزج للفصحى وتعبير ضعيف؛ التحسن جزئي |
| معنى دابا ومن بعد | تفسير أساسي مع أمثلة ضعيفة؛ انقطع الرد عند حد الاختبار 160 رمزًا |

هذه عينات محدودة وليست دليلًا على إتقان الدارجة. لا يصح وعد المستخدم بأن تعليمات جديدة أو إتاحة GitHub تعادل تدريبًا ناجحًا أو تجعل النموذج مطورًا مستقلًا.

## GitHub والتطوير

- تأكدت مصادقة `gh` الحالية بحساب `yosf-alaoui` في keyring، وصلاحية ADMIN على المستودع المعتمد. لم يُنسخ أو يُنشر رمز الدخول.
- أضيف `local-model/development-system.txt` لتوجيه العمل على المستودع، وتوثيق المهام، وتنزيل الأدوات اللازمة من مصادر تُراجع، واستخدام PM، وعدم تسريب الحالة الخاصة أو تعطيل الموافقات.
- اختيرت الشخصية `project-assistant` التي تجمع ملفي التعليمات في `agent.personalities`، دون تغيير نواة Hermes أو الأوزان أو محو الجلسات.
- فُعلت `terminal/file/skills` بالإضافة إلى `memory/session_search/todo` في `toolsets` و`platform_toolsets.cli`. الطرفية backend محلي ومجلدها المشروع.
- استُخدم الكاتب الذري الرسمي لحفظ config، مع snapshot محلي لملف الإعداد فقط قبل التغيير. تحققت إعادة القراءة من الشخصية والأدوات والحماية.
- وضع الموافقات النهائي `manual` مع `single_query_mode/unattended_mode/cron_mode: deny` وحماية ملفات التعليمات. قيمة `ask` الأولية تبين أنها غير معترف بها (رجع النظام إلى manual)، وصُححت إلى الاسم الرسمي.

## التحقق والحدود

حُلّت تعريفات الأدوات عبر registry وأثبت وجود أدوات الطرفية والقراءة والكتابة والتعديل والبحث والمهارات. نجح `skill_view` في قراءة مهارة GitHub المدمجة. نجح استدعاء `terminal` الأصلي لتشغيل `gh repo view`، وأعاد المستودع والصلاحية المطلوبة وخروجًا 0. ثم نزّل `gh api` ملف Modelfile العام عبر الأداة، وطابقت بايتاته الملف المحلي (491 بايت)، وحُفظت نسخة اختبار خارج المستودع.

الأدوات في الجلسات القديمة لا تُبدل تلقائيًا؛ محادثة جديدة تحمل المجموعة الحالية. تغيير الشخصية داخل محادثة قديمة مدعوم بأمر `/personality project-assistant` دون محو التاريخ، لكنه لا يمنح مجموعة أدوات جديدة.

الطرفية المحلية تعمل بصلاحيات مستخدم الجهاز والمصادقة الحالية، وليست عزلاً أو تقييدًا تقنيًا لمستودع واحد. لا توجد خدمة ذاتية تراقب GitHub أو تثبت أدوات وتطور في الخلفية. تنزيل الأدوات الممكن تقنيًا لا يبرهن جودة التخطيط أو البرمجة في نموذج 4B.

## نتيجة الاختبار الكامل والتعديل اللاحق

بدأ اختبار CLI فعلي على Hermes بقصد قراءة معلومات المستودع فقط. بلغ السياق 13395 رمزًا، وقُطع أول stream بعد 900 ثانية بلا أجزاء رد. أعاد النظام المحاولة مستفيدًا من cache جزئي، لكن النموذج استدعى terminal بأمر غير صحيح (خلط تنفيذ gh مع source واختلق صيغة API). رفضت بوابة التشغيل غير المراقب محاولة shell غير المناسبة، وفشل الأمر التالي؛ لم يُمنح تجاوز للحماية. أوقفت جلسة الاختبار وحدها عبر SIGINT، بعد التحقق من سجل lease ومعرّف الجلسة ووقت بدء العملية والمصنف الرسمي؛ لم تُقتل عمليات المستخدم أو Ollama.

اختُصرت تعليمات التطوير بالإنجليزية لتقليل الرموز، مع بقاء سياسة الدارجة والأمان والاستمرارية، وأضيف مثال صحيح لتشغيل gh كبرنامج. أضيف مزود محلي مسمى local-project على عنوان Ollama نفسه، بتمرير temperature=0.2 وpresence_penalty=0 عبر request_overrides. أكد resolver وصول الإعدادين. رُفعت مهلة stale إلى 1800 ثانية والطلب إلى 1900 لهذا النموذج وحده، مع استعادة أي إعدادات provider عامة سابقة من snapshot. لا يتغير تعريف Ollama أو الأوزان أو بصماتها بهذا الضبط.

نجح اختبار تالٍ محدود بسياق أقصر وأداة terminal واحدة: ولّد النموذج أمر gh repo view الصحيح (71.6 ثانية)، ونُفذ عبر handler الأصلي فأعاد اسم المستودع وADMIN بخروج 0، ثم نقل النموذج النتيجة الصحيحة (7.4 ثانية). هذا يثبت حالة قراءة محدودة، ولا يثبت أن مسار Hermes الكامل صار سريعًا أو أن النموذج يجيد جميع أعمال GitHub. لا تدّع نجاح اختبار كامل بعد التعديل؛ لم يُعاد بعد هذه المهلة الطويلة.

تأكدت وظائف بدء TUI من اختيار أدوات التطوير والشخصية الجديدة، وتأكد وجود gh في PATH الطرفية. اجتازت روابط الاستمرارية وdiff وفحوص agents-md/case-collisions/health. لا توجد تغييرات Python أو JavaScript في هذه المرحلة؛ التعديل ملفات تعليمات وتوثيق وإعداد محلي.

أعيد سؤالان عن الدارجة بالإعداد الأخير. الجواب الأول مفهوم لكنه كتب «إيهيه» بدل التعبير المعتاد، والثاني بقي فيه ضعف نحوي وأعاد السؤال بدل تقديم بداية عملية واضحة. لا تُعتبر الدارجة محلولة بالكامل. الاختبارات الأخيرة حافظت على التعليمات الأصلية للحماية والموافقات؛ لا يوجد تدريب للأوزان.

لوحظ أيضًا أن خادم dashboard القديم رفض قائمة النماذج بسبب اختلاف نسخة التشغيل عن HEAD، لذا يلزم إعادة تشغيله عبر دورة التشغيل الأصلية بعد نشر هذه المرحلة. قاعدة المحادثات لم تُستبدل.

نُشرت ملفات التعليمات والتوثيق، وأعيد تشغيل dashboard عبر `--stop` ضمن مجلد البيانات الحالي ثم ملف التشغيل الأصلي. نجحت صفحة المحادثة وAPI المصادق لقائمة النماذج دون خطأ النسخة القديمة؛ أكد API اختيار my-agent:qwen3.5-4b والمزود custom:local-project والشخصية project-assistant والموافقات manual. بعد نشر سجل التحقق يُعاد تشغيله مرة أخيرة لتحميل HEAD النهائي، لأن بوابة النسخة تعتمد HEAD حتى عند تغيير التوثيق وحده.
